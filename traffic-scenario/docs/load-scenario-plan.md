# 부하 시나리오 선정과 구현 계획

## 1. 결론

부하 시나리오는 **상품 100만 건에서 고객이 몰려 검색 서버가 요청을 거절하는 상황**으로 정한다. Codex 에이전트는 조회 방식을 확인하고 검색 인덱스를 추가한 뒤, 같은 요청 계획으로 다시 재서 개선을 확인한다.

로컬 측정에서 이 조건은 실패율 42.9%에서 0%로, p95 응답 시간 3,111ms에서 3ms로 바뀌었다. 실패는 모두 서버가 직접 돌려준 거절 응답이었다.

## 2. 스터디 목표와 기획에 맞는 이유

- 스터디 목표는 Codex로 성능 문제를 재고, 고치고, 좋아졌는지 확인하는 것이다. 이 시나리오는 그 세 단계가 그대로 나온다.
- 구현계획 문서가 첫 병목 후보를 인덱스 없는 조회로, 첫 개선 후보를 인덱스 추가로 정해 두었다. 서버와 전후 비교 기능도 이 전제로 만들어져 있다.
- 팀의 최소 목표는 시나리오 하나가 진짜 요청, 문제 발생, Codex 수정, 다시 확인까지 끝까지 도는 것이다. 이 시나리오는 고치는 방법이 분명해서 완주 가능성이 가장 높다.

## 3. 시나리오를 고른 기준

먼저 아래 네 가지를 모두 통과해야 한다.

| 기준 | 필요한 이유 |
| --- | --- |
| 실패 원인이 서버 안에 있다 | 부하를 보내는 쪽이 밀려서 생긴 실패는 서버를 고쳐도 줄지 않는다 |
| 코드나 DB 구조 수정으로 고쳐진다 | 전후 비교는 동시 처리 수 같은 설정값이 달라지면 판정을 거절한다 |
| 개선 폭이 측정 편차보다 크다 | 비교 정책 예시가 전후 각 3회 평균에서 응답 시간이나 처리량의 5% 이상 개선을 요구한다. 실패율은 조금이라도 줄면 개선으로 본다 |
| 한 바퀴가 몇 분 안에 끝난다 | 발표 시연에서 처음부터 끝까지 보여 줘야 한다 |

통과한 후보는 스터디 경험과의 연결, Codex가 로그를 읽고 원인을 골라야 하는 정도, 화면에서 보이는 정도, 다른 담당자의 코드를 고쳐야 하는 정도로 순위를 매긴다.

## 4. 측정 결과

맥 로컬에서 임시 포트와 별도 데이터 폴더로 쟀다. 저장소의 코드와 데이터는 바꾸지 않았다. 서버 설정은 기본값(동시 처리 4, 대기열 상한 200, 대기 제한 3,000ms)이고 고객 시간 초과는 5,000ms다. **조건마다 한 번씩만 쟀으므로 편차는 아직 모른다.**

### 조회 한 건의 속도

| 상품 수 | 인덱스 | 조회 중앙값 | 4개 동시 처리량 |
| --- | --- | --- | --- |
| 10만 | 없음 | 5.45ms | 초당 544건 |
| 10만 | 있음 | 0.29ms | 초당 7,324건 |
| 100만 | 없음 | 50.68ms | 초당 56건 |
| 100만 | 있음 | 0.30ms | 초당 7,793건 |

### 실제 서버에 1,000건을 보낸 결과

| 상품 수 | 유입 | 인덱스 | 실패율 | p95 응답 | 실패 내용 | 전송 지연 p95 |
| --- | --- | --- | --- | --- | --- | --- |
| 10만 | 2초 | 없음 | 28.9% | 4,850ms | 고객 시간 초과 289 | 904ms |
| 10만 | 2초 | 있음 | 0% | 5ms | 없음 | 1ms |
| 100만 | 25초 | 없음 | 0% | 863ms | 없음 | 1ms |
| 100만 | 10초 | 없음 | 42.9% | 3,111ms | 대기열 가득 참(429) 215, 대기 시간 초과(504) 214 | 1ms |
| 100만 | 10초 | 있음 | 0% | 3ms | 없음 | 1ms |
| 100만 | 2초 | 없음 | 78.7% | 4,671ms | 429 361, 504 80, 고객 시간 초과 346 | 515ms |
| 100만 | 2초 | 있음 | 0% | 5ms | 없음 | 1ms |

전송 지연은 부하 스크립트가 예정 시각보다 늦게 보낸 시간이다. 이 값이 크면 부하를 보내는 쪽도 함께 밀렸다는 뜻이다.

### 읽는 법

- **기존 설정(10만 건, 2초)도 인덱스로 고쳐진다.** 다만 실패가 모두 고객 시간 초과이고 서버의 거절 응답은 없다. 전송 지연도 904ms라 원인을 서버 기록만으로 설명하기 어렵다. 같은 조건을 앞서 한 번 더 쟀을 때는 실패율이 8.8%였으므로 편차도 크다.
- **100만 건, 10초 조건이 가장 깨끗하다.** 실패가 전부 서버가 돌려준 429와 504이고, 전송 지연이 1ms라 부하 스크립트는 밀리지 않았다. 서버 처리 한계(초당 약 40~56건)의 두 배 정도가 들어온 상황이다.
- 100만 건, 2초 조건은 실패가 더 크지만 부하 스크립트도 함께 밀린다.

## 5. 선택한 시나리오

| 항목 | 값 |
| --- | --- |
| 데이터 | 상품 100만 건 (생성 약 3초, 파일 84MB) |
| 기준 유입 | 1,000건을 10초에 (초당 100건) |
| 예상 증상 | 대기열 가득 참과 대기 시간 초과로 약 40% 실패 |
| Codex가 찾을 원인 | 조회 계획이 상품 전체를 훑고 임시 정렬을 한다 |
| 수정 | 카테고리, 가격, 상품 ID 순서의 인덱스 추가 |
| 확인 | 같은 요청 계획으로 재실험해 실패율과 응답 시간 비교, 검색 결과 동일성 확인 |

### 조건을 범위 안에서 랜덤으로 만드는 방법

- 랜덤으로 뽑는 값은 총 건수, 유입 시간, seed(같은 랜덤 결과를 다시 만들기 위한 씨앗 숫자)다.
- 범위는 측정값에서 정한다. 유입 속도는 서버 처리 한계의 1.5배에서 3배 사이인 초당 70~150건으로 둔다. 초당 200건을 넘기면 부하 스크립트의 전송 지연이 커지기 시작하므로 넘기지 않는다.
- 총 건수는 600~1,000건이다. 상한 1,000은 API 명세의 제한이다. 유입 시간은 건수를 유입 속도로 나눠 정한다.
- 랜덤은 요청 계획을 만들 때 한 번만 쓴다. 수정 전 3회와 수정 후 3회는 기준 실험의 계획을 그대로 재사용한다. 이렇게 해야 조건 차이로 생긴 착시가 없다.
- 수정이 끝난 뒤 새 seed로 한 번 더 돌려, 특정 계획에만 맞춘 수정이 아님을 확인한다.

몰렸다 빠지는 모양(봉우리 하나, 봉우리 둘, 계단)은 2단계에서 다룬다. 요청 계획을 만드는 코드가 제어 서버(`backend/manager.py`)에 있어서 담당자 협의가 필요하다.

## 6. 구현 계획

언어는 파이썬이다. 서버와 화면이 모두 파이썬이라 요청과 응답 정의를 그대로 쓸 수 있고 설치할 것이 늘지 않는다.

### 6.1 부하 시나리오

1. 한도 파일을 둔다. 유입 속도, 총 건수, 고객 시간 초과의 최소와 최대를 적는다.
2. 한도 안에서 조건을 뽑아 실험 시작 API를 호출하는 명령을 만든다. 뽑힌 값과 seed를 출력하고 기록한다.
3. 요청을 보내고 측정하는 부분은 기존 참조 실행기(`backend/loadgen.py`)를 그대로 쓴다. 서버와의 측정 약속이 이미 맞춰져 있기 때문이다.
4. 100만 건 데이터는 서버를 시작할 때 `MBM_PRODUCT_COUNT=1000000`과 새 `MBM_DATA_DIR`로 만든다. 실행 스크립트와 README 반영은 담당자와 협의한다.

### 6.2 Codex 에이전트

구현계획 문서 6장의 구성을 따른다. 왼쪽 터미널의 Codex가 에이전트이고, 아래 네 가지를 제공한다.

| 구성 | 내용 |
| --- | --- |
| 명령 도구 `agent_bridge/` | 실험 시작, 상태와 로그 조회, 서버 재시작, 같은 조건 재실험, 전후 비교, 진행 단계 전달. 실험과 재시작은 끝날 때까지 기다렸다가 결과를 JSON으로 돌려준다 |
| 되돌리기와 범위 보호 | 수정 전 상태를 기록하고, 결과가 나쁘면 코드와 인덱스를 함께 되돌린다. 허용한 두 파일 밖의 내용이 바뀌었으면 서버 재시작과 채택을 거절한다 |
| 작업 지침 `AGENTS.md` | 기준 실험 3회, 로그와 조회 계획 확인, 가설, 한 번에 한 가지 수정, 재시작, 재실험 3회, 비교, 유지 또는 복구 순서 |
| 플레이북 `knowledge/performance.md` | 스터디에서 겪은 문제를 증상, 확인 근거, 개선 후보, 검증 방법으로 정리 |

지침에 넣을 규칙은 다음과 같다.

- 실패를 먼저 부하 스크립트 쪽과 서버 쪽으로 가른다. 서버가 돌려준 429와 504, 전송 지연 값으로 판단한다. 스터디 6주차에 부하를 거는 쪽이 먼저 무너졌던 경험에서 온 규칙이다.
- 수정 범위는 검색 서버 코드(`backend/target.py`, `backend/catalog.py`)와 DB 구조다. 동시 처리 수 같은 설정값을 코드에 고정해서 우회하지 않는다.
- 검색 결과의 내용과 순서가 달라지면 빨라져도 개선으로 인정하지 않는다.

### 6.3 순서

1. 100만 건 조건을 3회 반복해 편차를 잰다.
2. 명령 도구와 테스트를 만든다.
3. 되돌리기와 범위 보호를 붙인다.
4. 작업 지침과 플레이북을 쓴다.
5. 실제 Codex로 한 바퀴를 돌린다.
6. 랜덤 조건을 붙인다.
7. 여유가 있으면 7장의 두 번째 시나리오를 추가한다.

## 7. 다른 후보와 판단

### 두 번째 시나리오 후보: 떠난 고객의 요청을 서버가 계속 처리

- 100만 건, 2초 조건에서 고객 346명이 5초 시간 초과로 떠났다. 검색 서버 코드는 요청이 취소돼도 실행 중인 조회를 끝까지 돌린다.
- 스터디에서 잰 경험과 이어진다. 입구가 29초에 응답을 끊었는데 함수는 35초까지 실행됐다.
- Codex가 고칠 내용은 이미 떠난 요청을 건너뛰는 기한 확인이다.
- 효과 크기는 아직 재지 않았다. 응답 시간 지표가 성공한 요청만으로 계산돼서, 실패가 줄고 느린 성공이 늘면 악화로 판정될 위험이 있다.

### 콜드 스타트 (제외)

- 서버 준비 시간은 0.6초였다. 재시작 직후 첫 5건의 응답 중앙값은 56.9ms, 이후는 55.3ms로 차이가 없었다. 새 프로세스의 첫 조회와 둘째 조회도 같았다.
- 이 서버에는 시작할 때 올리는 무거운 자원이 없어서 콜드 스타트가 생기지 않는다.
- 넣으려면 시작할 때 무거운 작업을 일부러 추가해야 하는데, 지연을 추가하지 않는다는 저장소 원칙과 어긋난다.
- 다시 검토할 시점: Codex의 개선으로 메모리 캐시가 생기면 재시작 직후 캐시가 비는 구간이 실제로 생긴다.

### 재시도 폭증 (독립 시나리오로는 제외)

100만 건, 인덱스 없음, 고객 1,000명을 10초에 보낸 결과다. 실패하면 최대 3번 다시 시도했다.

| 재시도 방식 | 서버 호출 수 | 최종 성공 | 성공까지 p95 |
| --- | --- | --- | --- |
| 없음 | 1,000회 | 733명 | 3.1초 |
| 즉시 재시도 | 1,816회 | 762명 | 3.1초 |
| 간격을 늘려 재시도 | 2,219회 | 837명 | 8.6초 |

- 재시도는 서버 호출을 약 두 배로 늘리지만 성공은 조금만 늘었다. 서버가 대기열이 차면 바로 거절해서 무너지지는 않았다.
- 재시도 방식은 요청을 보내는 쪽의 동작이다. Codex가 고치는 대상인 서버 코드 밖에 있다.
- 지금 측정 약속은 고객 한 명이 요청 하나를 보내는 것을 전제로 한다. 재시도를 넣으려면 그 약속을 담당자와 다시 정해야 한다.
- 넣는다면 독립 시나리오가 아니라 부하 조건의 하나로 넣는다. 수정 전후에 같은 재시도 방식을 고정하고 과부하를 더 크게 만드는 용도다.

### 차단 장치 (제외)

- 검색 서버는 외부 서비스를 호출하지 않아서, 죽은 상대를 기다리는 상황이 생기지 않는다.
- 넣으려면 검색 서버가 호출하는 별도 서비스를 새로 만들고 그 서비스를 일부러 고장 내야 한다. 서버 구조를 바꾸는 일이라 범위가 크다.

## 8. 팀과 정할 것

| 항목 | 내용 |
| --- | --- |
| 데이터 크기 | 시연 기본값을 100만 건으로 바꿀지 여부 |
| 비교 정책 | 예시 정책(전후 각 3회, 5% 이상 개선, 실패율 증가 금지)을 확정할지 여부 |
| 요청 계획 생성 | 몰리는 모양을 넣기 위해 제어 서버의 계획 생성부를 고칠지 여부 |
| 엘프와의 구분 | 메인 대시보드의 엘프는 데모 웹앱의 설정값을 조절한다. 이 에이전트는 검색 서버의 코드와 DB 구조를 고치고 같은 조건으로 다시 잰다 |

## 9. 한계

- 모든 측정은 맥 한 대에서 조건마다 한 번씩 했다. 장비와 실행 시점에 따라 값이 달라진다.
- 인덱스 구문이 저장소 코드에 이미 적혀 있다. Codex가 스스로 원인을 찾았다고 말하려면 조회 계획과 로그를 근거로 남기게 해야 한다.
- 측정에 쓴 스크립트는 임시 폴더에 있고 저장소에는 넣지 않았다.

## 10. 세 조건 측정 결과 (2026-11-28)

상품 100만 건, 1,000건을 10초에 보내는 같은 요청 목록(seed 42)으로 쟀다. 서버 코드는 고치지 않았다. 주지표는 예정한 검색 중 대기 한도 안에 올바른 결과를 받은 비율이다. 올바른 결과인지는 같은 검색을 DB에 직접 실행한 값과 대조했다.

확인한 것

- A는 같은 조건 3회에서 53.5~55.6%로 2.1%p 안에서 움직였다. A와 C의 차이(약 45%p)는 이 흔들림보다 훨씬 크다.
- C는 3회 모두 100%였다. 정상 상태 대조군으로 쓸 수 있다.
- B에서 서버는 떠난 고객의 요청을 계속 처리했다. B-1에서는 떠난 705건 중 485건의 검색을 끝까지 실행했고 검색 시간 합계는 45.5초였다. 서버가 이탈을 인지한 기록은 0건이었다.
- 세 조건 모두 예정한 1,000건이 전부 전송됐다. 부하를 보내는 쪽 문제는 없었다.

확인하지 못한 것

- B를 고쳤을 때의 효과. 저장소 밖 복사본에서 검색을 시작하기 직전에 연결이 끊겼는지 확인하도록 고쳐 봤으나, 서버가 끊긴 연결을 한 번도 감지하지 못했다(482회 확인 중 0회). 원인은 찾지 못했다.
- B는 인덱스가 없을 때만 나타난다. 인덱스가 있으면 모든 요청이 수 ms 안에 끝나 떠나는 고객이 없다. A와 독립된 두 번째 원인으로 쓰기는 어렵다.

판단

- A와 C는 시나리오로 쓴다.
- B는 재현은 되지만 고치는 방법과 효과가 확인되지 않아 보류한다.

## 11. 명령 도구로 한 바퀴 돌린 결과 (2026-11-28)

`agent_bridge` 명령만으로 실험부터 판정까지 돌렸다. 수정은 사람이 Codex 대신 넣었다. Codex는 아직 실행하지 않았다. 조건은 상품 100만 건이고 `run --random --seed 7`이 고른 765건을 8.6초에 보내는 요청 목록이다.

출발 상태 이름은 a(검색 병목)와 b(재고 재조회)와 c(정상)다. 여기의 b는 10번에서 보류한 B(떠난 고객)와 다른 것이다.

| 출발 상태 | 넣은 수정 | 기한 내 정답 (수정 전 3회) | 수정 후 3회 | 판정 |
|---|---|---|---|---|
| a 검색 병목 | 빈 목록을 바로 반환 | 67.7% 67.3% 66.4% | 0% 0% 0% | reject |
| a 검색 병목 | 검색 인덱스 추가 | 위와 같음 | 100% 100% 100% | accept |
| b 재고 재조회 | 재고 확인 삭제 | 22.0% 21.2% 20.9% | 0% 0% 0% | reject |
| b 재고 재조회 | 한 번의 조회로 합침 | 위와 같음 | 100% 100% 100% | accept |

- 틀린 수정 두 가지는 응답이 빨라졌지만 결과가 기준 정답과 달라 기각됐다. 기각 뒤 `rollback`으로 코드가 수정 전 상태로 돌아간 것을 확인했다.
- b는 검색 인덱스가 있는 상태에서 실패가 난다. a와 원인이 겹치지 않는다.
- b는 일부러 심은 결함이다. 품절 상품을 빼고 안내하는 규칙을 넣으면서 상품마다 재고를 새 연결로 따로 조회하게 만들었다. 상품의 1%만 재고가 있어 검색 한 번에 약 80ms가 걸린다. 가짜 지연은 넣지 않았다.
- 9번 한계에 적은 내용 중 조건마다 한 번씩만 쟀다는 점은 10번과 11번의 3회 반복으로 보완했다.

남은 것

- Codex를 실제로 실행해 같은 절차를 스스로 밟는지 확인하지 않았다.
- 인덱스 구문이 `backend/catalog.py`와 `README.md`에 그대로 있다. a에서 Codex가 이것을 읽고 답을 알 수 있다.
- 고르지 않게 몰리는 도착 모양은 넣지 않았다. 요청은 같은 간격으로 도착한다.
- 판정 정책 `demo-v1`은 예시 값을 그대로 썼다.

## 12. 리뷰 반영과 가장자리 조건 측정 (2026-11-28)

다른 AI 에이전트의 리뷰를 받아 판정과 되돌리기를 고쳤다.

| 고친 것 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 채택 조건 | 지표만 나아지면 고객 성공률이 목표에 못 미쳐도 accept | 수정 후 반복 실험이 전부 고객 목표(99%)를 채워야 accept |
| 반복 실험 채점 | 대표 실험 한 건씩만 채점 | 서버가 평균에 넣은 반복 실험을 전부 채점. 하나라도 측정 무효면 판정하지 않음 |
| 기준 정답 | 채점할 때마다 현재 DB에서 다시 계산 | 실험할 때 실험 폴더에 저장하고 재실험은 처음 실험의 정답을 물려받음 |
| 측정 무효 처리 | 서버 비교가 먼저 실패해 명령이 오류로 끝남 | 유효성을 먼저 확인하고 measurement_invalid로 답함 |
| 수정 범위 확인 | 기준 저장 전에 이미 바뀌어 있던 파일은 검사에서 빠짐 | 파일 내용 해시로 비교하고 범위를 벗어나면 서버 재시작부터 거절 |
| 되돌리기 | git 명령으로 복구해 중간에 실패하면 코드가 어중간하게 남음 | 기준 저장 때 복사해 둔 backend 폴더로 복구 |
| 출발 상태 전환 | 고친 코드가 남아 있어도 DB를 먼저 바꿈 | backend에 남은 변경이 있으면 DB를 바꾸기 전에 멈춤 |

무작위 조건 범위의 양 끝에서 세 출발 상태를 쟀다. 여섯 칸 중 다섯 칸을 한 번씩 쟀고 b의 가장 센 조건은 재지 않았다. 상품 100만 건이고 대기 한도는 5초다.

| 출발 상태 | 600건을 8.57초에 (가장 약함) | 1,000건을 6.67초에 (가장 셈) |
|---|---|---|
| a 검색 병목 | 90.7% degraded | 42.4% degraded |
| b 재고 재조회 | 29.2% degraded | 재지 않음 |
| c 정상 | 100% healthy | 100% healthy |

- a는 가장 약한 조건에서 90.7%로 목표 99%에 못 미치지만 여유가 작다. 같은 조건의 다른 요청 목록 3회는 94.8% 94.7% 등 평균 93.7%였다.
- 가장 약한 조건의 a에서 인덱스를 추가해 3회 다시 재니 100%였고 판정은 accept였다. 전후 각 3회가 채점됐다.

두 번째 리뷰에서 고친 것

| 고친 것 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 비교하는 실험 묶음 | 서버가 지난 시연의 실험까지 모아 3회를 채울 수 있었음 | 도구가 이번 시도의 실험을 기록하고 기준과 후보 각 3회가 전부 유효해야 판정. 서버가 다른 실험을 섞었으면 measurement_invalid |
| 대기 한도 | 성공 응답이면 늦게 와도 성공으로 셈 | 전송 지연과 응답 시간의 합이 대기 한도를 넘으면 성공에서 뺌 |
| 정답 없는 재실험 | 현재 DB를 새 정답으로 저장 | 처음 실험의 정답 기록이 없으면 measurement_invalid |
| 기준 저장 | 이전 복사본을 먼저 지우고 새로 복사 | 새 복사본을 완성하고 확인한 뒤 교체. 되돌릴 때도 복사본을 먼저 확인 |
| 출발 상태 전환 | 결함 파일을 뺀 뒤에 남은 변경을 발견하고 멈춤 | 코드가 알려진 출발 상태와 정확히 같을 때만 코드와 DB를 바꿈 |
| 수집 누락 | 명령이 오류로 끝남 | measurement_invalid와 사유를 돌려줌 |
| 기준에 성공이 0건 | 후보가 완전히 정상이어도 reject | 사유를 붙여 hold |

같은 요청 목록으로 한 바퀴를 두 번 돌리니 두 번째는 measurement_invalid가 나왔다. 서버가 첫 번째 바퀴의 실험을 섞었기 때문이다. 새 요청 목록(600건을 8.57초에)으로 다시 돌리니 수정 전 3회 평균 92.4%와 수정 후 3회 100%로 accept가 나왔다.

부하 범위의 아래쪽은 올리지 않는다. 가장 약한 조건에서도 a의 3회 평균은 목표보다 5%p 이상 낮았다. 시연 장비에서 같은 조건으로 a와 c를 반복해 본 뒤 정한다.

세 번째 리뷰에서 고친 것

| 고친 것 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 정답 없는 재실험의 재채점 | 다시 채점하면 재실험이었다는 사실을 잊고 현재 DB로 채점 | 실험 폴더에 출처를 남겨 다시 채점해도 measurement_invalid |
| 대기 한도를 모르는 실험 | 설정 파일이 없으면 기본값 5초로 채점 | 설정이나 원본 기록이 없거나 손상됐으면 measurement_invalid |
| 지난 후보의 판정 | 서버를 다시 시작한 뒤에도 지난 후보로 비교하면 accept가 다시 나옴 | 후보 실험 뒤에 재시작이 있었으면 measurement_invalid |
| 보내는 쪽이 늦은 실험 | 보내기 전에 대기 한도를 다 쓴 요청 때문에 서버가 degraded로 분류됨 | 그런 요청만으로 목표를 놓치면 measurement_invalid와 사유를 돌려줌 |
| 기준 저장의 마지막 교체 | 이름 바꾸기가 실패하면 이전 복사본이 없어짐 | 새 기준을 폴더째 완성하고 가리키는 파일만 교체 |
| 출발 상태 확인 | 스테이징만 한 새 파일을 놓침. DB 준비가 실패하면 결함 파일만 남음 | 스테이징한 파일도 잡음. DB를 먼저 확인하고 실패하면 코드를 복구 |
| 재시작 기록 | 서버가 재시작을 거절해도 실험 묶음이 나뉨 | 서버가 받아들인 뒤에만 나눔 |
| 성공 0건인 기준 실험 | 세 번 모두 0건일 때만 hold | 한 번이라도 0건이고 후보가 정상이면 hold |

새 요청 목록(600건을 8.57초에, `--seed 44`)으로 a에서 한 바퀴를 다시 돌렸다. 수정 전 3회 평균 84.8%와 수정 후 3회 100%로 accept가 나왔다. 되돌리고 재시작한 뒤 같은 후보로 다시 비교하니 measurement_invalid가 나왔다. 수정 전 값이 앞의 측정(92.4%)보다 낮은 것은 서버가 거절한 응답이 137건에서 273건으로 늘었기 때문이다. 대기 한도를 예정 도착 시각부터 세게 바꾼 것 때문에 빠진 정답은 두 측정 모두 0건이었다. 요청 목록과 측정 시점이 달라서 거절이 늘어난 원인은 특정하지 못했다. 인덱스의 효과로 볼 수 있는 값은 같은 요청 목록에서 나아진 15.2%p다.

- 기준 실험: run-1b66efbe08894a0882b6 run-b086c713081e40c6847f run-dd116258f622457eba41
- 후보 실험: run-1b56187b603d473b8b4d run-66aab496a223444e83bd run-89f0ddf699384f0f8920
- 이 기록은 임시 데이터 폴더에 있고 저장소에는 넣지 않았다.

리뷰 지적 중 고치지 않은 것

- 에이전트가 읽는 저장소에 원인 설명과 인덱스 구문이 있다. 출제용 폴더와 진단용 폴더를 나눠야 풀린다.
- 되돌리기는 DB에서 지워진 객체와 바뀐 데이터를 복구하지 못한다. 없어진 객체 이름만 알려 준다.
- 되돌리기는 기준 저장 뒤 backend에 생긴 파일을 누가 만들었는지와 무관하게 지운다. 실험 중에는 사람이 backend를 고치지 않아야 한다.
- 이번 시도의 실험 기록(`bridge-runs.jsonl`)은 데이터 폴더에 있어 에이전트가 고칠 수 있다. 지우면 측정 무효가 되지만 고쳐 쓰는 것은 막지 못한다. 막으려면 기록을 제어 서버가 보관해야 한다.
- 측정이 무효일 때 같은 요청 목록에 실험을 더 보태도 회복되지 않는다. 되돌린 뒤 새 요청 목록으로 처음부터 다시 잰다.
- 요청이 서버에 실제로 도착했는지는 고객 쪽 기록만으로 판단한다. 서버 수신 기록과 한 건씩 맞춰 보지 않는다.

## 19. 검증 쪽과 에이전트의 권한 분리 (2026-11-28)

18번까지는 Codex가 검증기와 실험 기록을 고칠 수 있었고 원본 저장소의 답도 읽을 수 있었다. 바뀐 것을 나중에 잡아내는 수준이었다. 처음부터 읽지 못하고 쓰지 못하게 바꿨다.

- 평가 폴더를 심판 폴더와 작업 폴더로 나눴다. 검증기와 정책과 정답과 실험 기록은 심판 폴더에 두고 Codex는 작업 폴더에서 일한다.
- 작업 폴더의 실험 도구는 명령을 심판 프로세스에 전달하는 코드 한 파일이다. 채점과 판정과 되돌리기는 심판 프로세스가 한다.
- 심판 폴더의 검색 서버는 작업 폴더의 `backend/catalog.py`와 `backend/target.py`를 링크로 가리켜 실행한다.
- Codex의 권한 프로필로 전체 디스크 읽기를 끄고 작업 폴더 쓰기와 실험 기록 읽기만 연다.
- 평가 한 번을 처음부터 끝까지 실행하는 `evals/runner.py`를 만들었다. 실행 시간 한도가 있다.

위 권한을 건 샌드박스에서 직접 시험한 결과

| 시도 | 결과 |
|---|---|
| 심판 폴더의 검증기 읽기 | 거부 |
| 원본 저장소의 결함 파일 읽기 | 거부 |
| 실험 기록 폴더에 쓰기. 직접 쓰기와 링크를 거친 쓰기 | 거부 |
| 실험 묶음 기록 고쳐 쓰기 | 거부 |
| Skill과 명령 전달 코드 고쳐 쓰기 | 거부 |
| 허용하지 않은 명령 `scenario` | 거부 |
| 실험 기록 읽기, 서버 코드 고치기, DB에 인덱스 추가 | 허용 |
| 넘겨받기, 재실험, 범위 확인, 재시작, 비교, 되돌리기 | 실행됨. 되돌린 뒤 두 폴더 모두 변경 없음 |

- 이 시험은 Codex의 샌드박스 명령으로 했다. Codex를 실제로 실행하지는 않았다. `codex exec`가 같은 권한을 적용하는지와 새 구조에서 Codex가 Skill의 절차를 따르는지는 실제 실행으로 확인해야 한다.
- 시험 중에 서버를 켠 직후의 첫 유입이 측정 무효로 나온 일이 있었다. 전송이 늦었다는 사유였다. 이어진 재실험은 유효했다. `runner.py`는 유입이 무효면 세 번까지 다시 보낸다.

## 20. 권한을 분리한 구조에서의 Codex 실제 실행: a (2026-11-28)

19번의 구조로 출발 상태 a를 한 번 실행했다. `evals/runner.py`가 폴더 생성부터 채점까지 했다. 모델은 `gpt-6.2-astra`이고 생각 단계는 `medium`이다. 걸린 시간은 147초다.

| 항목 | 결과 |
|---|---|
| 유입 | 890건을 9.37초에. 496건(55.73%)이 기한 내 정답 |
| Skill 사용 | 첫 명령으로 `SKILL.md`를 읽고 절차를 따름 |
| 넘겨받기 | `snapshot` 후 `adopt`. 유입을 새로 보내지 않음 |
| 증거 조회 | 관측 방법 문서, 검색 코드, 실행 계획 기록, 서버 이벤트의 대기와 처리 시간 중앙값(대기 2,938ms와 처리 96ms) |
| 기준 3회 | 55.73~57.87%. 평균 56.86% |
| 가설 기록 | 첫 수정 전에 `progress`로 가설과 예상 결과와 기각 조건을 남김 |

| 수정 후 3회 | 모두 890건 성공 |

- 권한 프로필이 실제 실행에 적용됐다. Codex에 전달된 실행 환경 정보에 평가 폴더 전체 거부와 작업 폴더 쓰기와 전체 디스크 거부가 들어 있었다.

- 실패한 명령이 두 개 있었다. 작업 폴더에 없는 `agent_bridge/README.md`를 읽으려 했고 `pytest`가 없는 파이썬으로 테스트를 실행하려 했다. 둘 다 작업 폴더의 `AGENTS.md`가 없는 것을 가리켜서 생겼다. 작업 폴더를 만들 때 그 줄을 빼도록 고쳤다.

- 원본 기록은 임시 폴더에 있고 저장소에는 넣지 않았다. b와 c는 이 구조로 아직 실행하지 않았다.

## 21. 실행 방법 단순화와 AGENTS.md 원복 (2026-11-28)

- `demo` 스크립트를 추가했다. `./demo a`가 환경변수 지정과 상품 DB 생성과 출발 상태 전환과 서버 시작을 하고 `./demo surge`가 유입을 보낸다. 터미널마다 환경변수를 다르게 쳐서 서로 다른 데이터 폴더를 보는 실수를 막는다.
- Codex에게 주는 요청 앞에 `$performance-repair`를 붙여 Skill을 이름으로 부른다. Codex의 기본 지침에 사용자가 Skill을 이름으로 부르면 그 Skill을 작업 계획에 넣으라는 문장이 있는 것을 확인했다.
- `AGENTS.md`를 원래 내용으로 되돌렸다. 이 파일은 이 폴더에서 코드를 쓸 때의 주석 규칙이고 성능 문제를 고치는 에이전트의 행동 규칙과 목적이 다르다. 수정 범위는 Skill로 옮겼다.
- 요청에 Skill 이름을 붙이고 `AGENTS.md`의 안내를 뺀 상태로는 Codex를 아직 실행하지 않았다. 20번의 실행은 `AGENTS.md`가 Skill 위치를 알려 주던 때의 것이다.

## 22. 화면의 고객 급증 단축키를 무작위 조건으로 변경 (2026-11-28)

화면의 `t` 키는 1,000건을 2초에 보내는 고정 조건이었다. 출발 상태 a에서 측정 무효가 나서 쓰지 못했고 무작위 유입은 다른 터미널의 `surge` 명령으로만 보낼 수 있었다.

- `frontend/session.py`를 고쳤다. 조건을 지정하지 않은 고객 급증은 `agent_bridge/limits.json` 범위에서 요청 수와 속도와 seed를 무작위로 고른다. 화면 터미널 하나에서 `t` 키로 무작위 유입을 보낼 수 있다.
- 조건을 직접 지정하는 `./market experiment surge <건수> <초>`와 평소 방문 `n` 키는 그대로다.
- 출발 상태 a와 b와 c는 단축키로 만들지 않았다. 출발 상태는 서버가 꺼져 있을 때 코드와 DB를 바꾸는 것이라 화면이 켜진 뒤에는 바꿀 수 없다. `./demo a`처럼 켤 때 고른다. 유입 단축키는 세 상태에 똑같이 쓴다.
- 화면과 서버 코드 가운데 이 도구 작업으로 고친 곳은 이것이 처음이다. `frontend/session.py`와 `tests/test_frontend.py`와 `README.md`와 `docs/traffic-frontend.md`다.
- 화면을 실제로 켜서 `t` 키를 눌러 보지는 않았다. 테스트로 요청 본문이 범위 안에서 매번 달라지는 것을 확인했다.

## 23. 채택된 수정을 PR로 올리는 명령 (2026-11-28)

채택된 수정을 저장소에 바로 남기지 않고 PR로 올려 사람이 검토한 뒤 병합하게 했다. 방식은 저장소 루트의 `fixer.py`(버그 수정 병정의 PR 생성)를 따랐다.

| 항목 | `fixer.py` | `agent_bridge/publish.py` |
|---|---|---|
| 올리는 조건 | 패치가 한 곳에 맞고 문법이 맞음 | `compare`의 판정이 accept이고 수정 범위 확인을 통과함 |
| 작업 위치 | 별도 git worktree의 새 브랜치 | 같음 |
| 브랜치 이름 | `sentry-bot/<이슈>-<시각>` | `perf-bot/<실험 번호>-<시각>` |
| 기준 브랜치 | `XMAS_FIX_BASE`. 기본 main | `XMAS_FIX_BASE`. 기본은 현재 브랜치 |
| 중복 방지 | `.runtime/prs.json` | `.runtime/perf-prs.json`. 같은 실험은 한 번만 |
| 병합 | 사람 | 사람 |

- `./demo pr`은 올릴 내용만 보여 주고 `./demo pr --publish`가 실제로 올린다. PR 본문에 수정 전후의 기한 내 정답 비율과 판정과 실험 번호가 들어간다.
- DB에만 한 변경은 PR에 담기지 않는다. Skill에 DB 구조 변경을 코드에도 넣으라는 규칙을 넣었다.
- 실제로 PR을 올려 보지는 않았다. 명령 순서와 조건은 테스트로 확인했다.
- 아직 하지 않은 것: Codex는 여전히 켜져 있는 서버의 코드를 직접 고친다. 운영 서버와 시험 서버를 따로 두는 것은 만들지 않았다.
- `./demo codex`의 생각 단계를 `medium`으로 고정했고 실험 기록 위치를 명령 결과의 `records_dir`로 알려 주게 했다. 직전 실행에서 Codex가 기록 폴더를 찾지 못한 적이 있었다.

## 24. Codex 모델과 생각 단계 고정 (2026-11-28)

- `./demo codex`와 `evals/runner.py`가 쓰는 모델을 `gpt-6.2-sol`로, 생각 단계를 `medium`으로 고정했다. 실행하는 사람의 평소 Codex 설정에 따라 결과와 사용량이 달라지지 않게 하기 위해서다.
