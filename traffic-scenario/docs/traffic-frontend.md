# 트래픽 부하 화면

기존 버그 픽스 화면의 픽셀아트와 렌더러 및 키보드와 마우스 입력 방식을 재사용한 트래픽 전용 화면이다. `main`의 버그 픽스 화면을 새로 구현하지 않는다. 프론트와 실행 파일 및 문서는 모두 `traffic-scenario/` 안에 있다. 이 문서의 명령은 해당 폴더에서 실행한다. 상위 폴더의 기존 픽셀 렌더러는 수정 없이 불러온다.

## 현재 작업 폴더에서 실행

```bash
./run.sh
```

현재 `traffic-scenario/` 폴더에는 `.venv`가 준비돼 있다. 다른 환경에서는 Python 3.11 이상으로 먼저 설치한다.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.lock
./run.sh
```

이 스크립트는 우리 FastAPI 백엔드와 트래픽 화면을 함께 실행한다. 8000번과 8001번 포트를 사용한다. `q`로 종료하면 스크립트가 시작한 서버도 종료된다. 진행 중 실험은 먼저 중지한 뒤 결과 수집을 기다린다. 로그는 `data/control-process.log`에 남는다.

화면은 백엔드 준비가 끝난 뒤 열린다. 기존 프로세스가 포트를 사용 중이면 중복 실행하지 않고 안내한다. 재시작하면 같은 서버에서 진행 중인 실험에만 다시 연결한다. 완료와 중지 및 실패로 끝난 실험은 자동으로 불러오지 않고 빈 마켓으로 시작한다. 과거 실험을 직접 열어도 기존 완료·실패 고객은 다시 움직이지 않는다. 검색 서버 재시작으로 수집이 중단된 이전 실험은 기록을 보존하고 비교에서 제외하며 새 실험을 막지 않도록 처리한다. 외부 관리 서버의 미회수 요청은 자동으로 해제하지 않는다.

기존 백엔드가 이미 실행 중이면 프론트만 실행한다.

```bash
python3 -B -m frontend --server http://127.0.0.1:8000
```

처음부터 트래픽 화면으로 들어간다. 이 모드에는 버그 픽스 화면 전환 버튼을 표시하지 않는다. 프론트에는 Textual 등 새 패키지가 필요하지 않다.

## 화면 조작

| 조작 | 동작 |
| --- | --- |
| 평소 방문 클릭 또는 `n` | 고객 1000명을 30초 동안 유입 |
| 고객 급증 클릭 또는 `t` | 고객 1000명을 2초 동안 유입 |
| 중지 클릭 또는 `x` | 추가 요청을 중지하고 전송한 결과 회수 |
| 재실험 클릭 또는 `r` | 같은 요청 계획으로 재실험 |
| 비교 클릭 또는 `c` | `demo-v1` 정책으로 기준 실험과 비교 |
| 고객 클릭 또는 `j/k`와 Enter | 실제 고객 요청과 측정 시간 조회 |
| 개선 안내 클릭 또는 `g` | 외부 성능 개선 에이전트 연결 안내 |
| Space | 화면 연출 정지. 백엔드 실험은 계속 진행 |
| `q` | 화면 종료 |

대기 고객은 실제 서버 이벤트를 사용한다. RPS가 증가했다는 이유로 대기 고객을 만들어내지 않는다. 옷과 모자 색은 고객마다 유지한다. 머리 위 표시는 안내소 방문 이후부터 실제 요청 상태를 사용하며 `…`는 대기 파란 `?`는 처리 중 초록 `+`는 완료 빨간 `!`는 실패다.

트리는 중앙에 두고 왼쪽 4개와 오른쪽 4개의 상점 및 병정을 좌우 대칭으로 배치한다. 상점 폭은 9칸이며 상점 사이 간격은 5칸이다. 상점 이름은 중복 없이 가운데 정렬하며 좌우에 네 가지 지붕 색을 고르게 섞는다. 안내소는 광장 아래쪽 중앙에 있으며 파란 직원 한 명이 안내소를 담당한다. 초록 안내원은 개선 상태를 나타내는 캐릭터다. 8개 상점을 모두 보려면 터미널 폭 180열 이상을 사용한다. 좁은 화면에서는 배치 가능한 상점만 표시하고 필요한 폭을 안내한다. 같은 상품 종류의 상점이 여러 개면 요청별로 방문 상점을 분산한다. 안내소 직원 수는 화면 연출이며 실제 동시 처리 수는 백엔드 설정을 사용한다.

고객 동선은 `안내소 아래에서 입장 → 세로 대기줄 → 안내 → 요청 상품 상점 → 퇴장`이다. 성공 고객은 요청의 `query.category`에 맞는 상점 앞으로 이동한다. 실패 고객은 상점을 방문하지 않고 이탈한다. 상점 앞에 도착한 고객의 머리 위 표시가 노점과 겹치지 않도록 지면에 여유 공간을 둔다. 안내소와 상태 문구도 이동 동선과 분리한다.

조회 사이에 이미 완료된 짧은 요청은 일부 대표 고객의 이동 연출로 입장부터 상점 방문까지 보여준다. 이 고객의 결과 표시는 이미 관측한 실제 결과이며 이동 연출이 실제 응답 시간을 뜻하지 않는다. 화면에 표시 중이던 고객은 같은 위치와 옷을 유지한 채 다음 동선으로 연결한다. 실제 표시 중인 처리 고객 한 명만 안내 장면에 연결한다. 대표 고객은 성공과 실패를 번갈아 일정한 간격으로 추가하며 미표시 결과는 결과별 최근 32명으로 제한한다. 전체 요청 수와 실패율 및 응답 시간은 모든 실제 요청을 기준으로 집계한다.

실험 종료 후에는 새로운 대표 고객을 추가하지 않고 이미 화면에 있는 고객의 이동만 마무리한다. 하단에는 종료와 중지 결과 및 남은 이동 연출 여부를 표시한다. 안내소 아래 오른쪽에 현재 대기와 관측 최대 대기를 고정 표시한다. 관측 최대는 실제 대기 이벤트와 서버 집계에서 얻은 최댓값이며 대기가 해소돼도 유지하고 새 실험을 시작하면 초기화한다. 상태 문구는 버그마스 마켓 안내소 간판 위의 전용 공간에 표시하며 달 장식은 둥근 모양이다.

110열 이상에서는 오른쪽에 지표와 고객 상세를 표시한다. 좁은 화면에서는 마켓 아래에 표시한다. 최소 크기는 기존 화면과 같은 60열 × 22행이다. 오른쪽 상세를 함께 보려면 180열 × 44행을 권장한다.

## 왼쪽 Codex와 연결

기존 `market` 명령 파일과 `.runtime/state.json`을 그대로 사용한다.

```bash
./market experiment normal
./market experiment surge 1000 0.5
./market experiment stop
./market experiment replay
./market experiment compare demo-v1
./market experiment select customer-0001
./market status
```

`state.json`의 기존 필드는 유지하며 `experiment`에 실험 ID와 집계 및 에이전트 단계와 선택 고객을 추가한다. 팀원의 에이전트가 `POST /api/agent/progress`를 호출하면 실제 단계와 메시지를 표시한다. 개선 안내가 에이전트를 실행하거나 코드를 자동 수정하지는 않는다.

현재 프로젝트는 기본 비교 정책이 비어 있다. 비교하면 `POLICY_NOT_READY`가 표시된다. 팀이 정한 정책을 `config/policies.json`에 등록한 뒤 사용한다. 반복 횟수가 부족하면 `inconclusive`다.

## 기존 옆 패널과 연결

원래의 JSON 프레임 프로토콜을 그대로 지원한다.

```bash
python3 -B -m frontend --stream --size 100x30 --server http://127.0.0.1:8000
```

`blocks` 프레임과 키 및 클릭 명령 형식은 바꾸지 않았다. 실제 채팅 앱에 붙이는 설정은 내일 팀과 맞추면 된다. 별도의 웹 프론트는 만들지 않았다.

## 폴더 구조

```text
traffic-scenario/
├── backend/
├── frontend/
│   ├── app.py       # 트래픽 전용 실행과 입력 처리
│   └── session.py   # API 연결과 상태 및 화면 구성
├── tests/
├── docs/
├── market
└── run.sh
```

상위 폴더의 `xmas_market.py`와 `market` 및 README는 원래 상태로 복구했다. `frontend/app.py`에서 기존 `World`를 상속하고 그리기 유틸을 읽기 전용으로 재사용한다. 트래픽 코드가 공통 모듈을 덮어쓰거나 전역 함수를 바꾸지 않는다. 따라서 이 폴더는 공통 렌더러가 있는 merrybugmas 저장소 안에서 실행한다.

## 검증

```bash
.venv/bin/python -B -m pytest -q
```

백엔드 38개와 트래픽 프론트 38개 테스트를 실행한다. 옆 패널은 기존 JSON 프레임 형식을 사용한다. 자동 성능 개선 에이전트 실행은 별도 연결이 필요하다.

터미널은 바뀐 줄만 출력한다. 동기 출력 지원 터미널에서는 한 화면 갱신을 묶어 중간 프레임 노출을 줄인다. [xterm.js 동기 출력 문서](https://xtermjs.org/docs/api/terminal/interfaces/imodes/#readonly-synchronizedoutputmode)를 참고한다. 실제 VS Code 화면에서의 최종 깜빡임 여부는 터미널 버전과 렌더러에도 영향을 받는다.
