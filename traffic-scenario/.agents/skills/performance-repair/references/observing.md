# 성능 문제 관측 방법

원인을 정하기 전에 무엇을 어디서 볼 수 있는지 정리한 문서다. 원인과 해결책은 적지 않는다. 관측한 값으로 직접 판단한다.

## 먼저 확인할 것

- 예정한 요청이 실제로 전송됐는가. `planned`와 `sent`와 `dropped`와 `send_lag_p95_ms`를 본다. 부하를 보내는 쪽이 먼저 한계에 닿으면 서버는 문제없어 보인다.
- 실패가 어디서 났는가. `outcomes`에서 서버가 거절한 응답(429와 504)과 고객이 기다리다 떠난 것(timeout)을 구분한다.
- 지연 지표가 무엇을 잰 값인가. `server_metrics`의 응답 시간은 성공한 요청만으로 계산한다. 실패가 많으면 이 값만으로 판단하지 않는다. 고객 기준 결과는 `customer_success_rate`다.

## 요청 하나가 시간을 쓰는 곳

- `data/runs/<run_id>/` 아래에 실험 한 번의 원본 기록이 있다. `target/`에는 서버 이벤트 파일이 수백 개 있다. 파일 목록 전체를 출력하지 말고 필요한 파일만 읽는다.
- 서버 이벤트에는 요청마다 대기 시간(`queue_wait_ms`)과 처리 시간(`processing_ms`)이 따로 있다. 대기가 긴지 처리가 긴지에 따라 볼 곳이 달라진다.
- `GET /api/runs/<run_id>/requests/<request_id>`로 요청 하나의 전체 경과를 볼 수 있다.

## 처리 시간이 길 때 볼 것

- 검색 한 번이 DB에 보내는 조회가 몇 개인지 코드에서 센다.
- 각 조회가 표 전체를 읽는지 인덱스를 쓰는지 `EXPLAIN QUERY PLAN`으로 확인한다. `data/runs/<run_id>/query-plan.json`과 `schema.sql`에 실험 당시 값이 있다.
- 조회 하나를 따로 실행해 시간을 잰다. 서버 전체를 돌리지 않아도 된다.

## 판단할 때 주의할 것

- 한 번 잰 값을 평소 값으로 보지 않는다. 같은 조건 3회의 범위를 먼저 본다.
- 숫자를 쓸 때 그 숫자가 무엇을 잰 것인지 함께 적는다.
- 설정한 값대로 실제로 동작한다고 가정하지 않는다. 기록에서 확인한다.
- 수정 뒤에는 같은 요청 목록으로만 비교한다.
