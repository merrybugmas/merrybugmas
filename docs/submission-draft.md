## Ⅱ. 문제정의 및 프로젝트 목표

**○ 해결과제 및 프로젝트 목표**

장애가 나면 운영자는 트래픽(Grafana), 에러(Sentry), 자동 수정 봇(sentry-bot)의 진행 상황을 서로 다른 화면에서 맞춰 봐야 한다. 지금 무엇이 터졌는지, 봇이 무엇을 처리 중인지, 사람이 봐야 할 것은 무엇인지를 한눈에 알기 어렵다. 봇이 왜 그렇게 판단했는지는 더 보이지 않아, 자동화를 믿고 맡기기 어렵다.
MERRY BUGMAS 는 세 화면을 하나의 게임 장면으로 합친다. 트래픽은 상점 앞 대기열, 미해결 이슈는 쥐, 봇은 쥐를 잡는 호두까기 병정, 트래픽이 몰리면 레버를 당겨 해소하는 에이전트는 엘프 점원이다. 목표는 ① 숫자를 읽지 않아도 상황이 보이게 하고 ② 에이전트의 판단 근거를 화면에 남기며 ③ 운영자가 채팅 한 줄로 에이전트를 지휘하게 하는 것이다.

**○ 주요 대상 사용자·활용 방안**

- 온콜 개발자: 장애 대응 중 트래픽·에러·봇 상태를 한 화면에서 보고, 채팅으로 "WEB-2B1 먼저 처리" 처럼 우선순위를 바꾼다.
- 운영·프로덕트 담당자: 팀 모니터에 띄워 두고 줄 길이와 쥐 수로 서비스 상태를 직관적으로 파악한다.
- 자동화 봇을 도입하려는 팀: 봇이 이슈를 어떻게 판정(fixable / noise / 사람 필요)했고 왜 그랬는지를 기록으로 확인하며 신뢰를 쌓는다.
- 신규 입사자 교육: "트래픽이 늘면 에러가 늘고, 봇이 처리하고, 일부는 사람에게 넘어온다"는 운영 흐름을 게임으로 설명한다.

**○ 프로젝트 추진 목적 및 구현 목표**

추진 목적은 AI 에이전트를 운영에 들일 때 생기는 두 가지 벽, 즉 "에이전트가 뭘 하는지 안 보인다"와 "에이전트에게 말로 시킬 수 없다"를 낮추는 것이다.
구현 목표는 세 층이다.
1) 시각화: 터미널에서 의존성 없이 도는 픽셀아트 대시보드. 서비스 6개 × 시나리오 3개(트래픽·Sentry·개요)를 게임처럼 골라 본다.
2) 운영자 에이전트(Codex): AGENTS.md 를 도구 사용 규약으로 삼아, 사람 말을 대시보드 명령으로 바꾸고 현황을 숫자로 답한다. 자율 모드에서는 사람 없이 30초마다 상황을 판단해 지시한다.
3) 에이전트의 두뇌(OpenAI API): 자연어 명령 해석, 이슈 트리아지와 근거·수정 요약, 운영 브리핑, 트래픽 폭주 시 어떤 레버를 당길지를 구조화된 JSON 으로 받아 게임 동작에 바로 연결한다.
그리고 API 키가 없거나 호출이 실패해도 대시보드가 멈추지 않도록 키워드·mock 판정으로 이어지게 하는 것까지가 목표다.

## Ⅳ. AI 기술 활용 및 적용 방식

**○ OpenAI API·Codex 등 활용 기술 및 적용 기능**

- **Codex CLI — 운영자 에이전트**: 대시보드 옆 창에서 Codex 가 레포의 `AGENTS.md` 를 읽는다. 이 문서는 Codex 용 도구 사용 규약이다. 어떤 명령(`./market status · tell · focus · start · view · brief · say`)이 있는지, 답하기 전에 반드시 status 를 읽고 숫자로 답할 것, 코드를 고치지 말 것을 적어 두었다. 사용자는 "검색 쪽 버그 보여줘", "다들 뭐 하고 있어?" 처럼 말하기만 하면 된다.
- **Codex exec — 자율 운영 모드**: `tools/codex-autopilot.sh` 가 30초마다 `codex exec` 를 실행한다. Codex 는 현황을 읽고 가장 급한 일을 골라 최대 2개 명령을 내린 뒤, 판단 근거를 대시보드에 띄운다.
- **OpenAI API — 병정의 두뇌** (`ai.py`): Responses API 와 strict JSON Schema(Structured Outputs)로 세 가지 판단을 받는다.
  ① 명령 해석: 문장 + 현황 JSON → {병정, 행동, 이슈 ID, 대답}
  ② 트리아지: 이슈 제목 → {fixable / noise / needs-human, 근거, MR 수정 요약}
  ③ 브리핑: 현황 JSON → {요약 3줄, 권고}
  ④ 트래픽 대응(엘프): 부하·5xx·응답 시간·대기 요청·레버 상태·이미 써 본 레버 → {레버(cache/capacity/waitroom/human/none), 근거, 할 말}
  ⑤ 수정 패치(`fixer.py`, 실연동 fixable 이슈): 이슈 + 레포 소스 → {파일, 찾을 문자열, 바꿀 문자열, PR 제목·설명}. 패치가 정확히 한 곳에 맞고 문법 검사를 통과할 때만 새 브랜치에 커밋해 PR 을 연다

**○ 프로젝트 내 AI 기술의 역할 및 주요 동작 방식**

(그림: `docs/images/architecture.png` — 사람 → Codex → `./market` → 대시보드 ↔ OpenAI API, 그리고 `--live` 실연동 3곳: Sentry API(읽기) · 서버 `/metrics`·레버 · GitHub PR)

1. 사람(또는 자율 모드)이 Codex 에게 말한다. Codex 는 `./market status` 로 `.runtime/state.json`(1초마다 갱신)을 읽고 판단한다.
2. Codex 가 `./market tell 진저 …` 를 실행하면 `.runtime/cmd` 를 거쳐 대시보드에 바로 반영된다.
3. 대시보드는 명령 문장을 OpenAI API 에 넘겨 구조화된 의도로 받는다. 새 이슈(쥐)가 생기면 트리아지를 요청하고, 병정은 판정이 올 때까지 "AI 판정 중" 말풍선으로 기다린다.
4. 판정 근거와 수정 요약은 작전 로그(🧠)와 잡은 쥐 기록에 남아, 에이전트가 왜 그렇게 했는지 사람이 확인할 수 있다.
5. 안정성 설계: API 호출은 백그라운드 스레드에서 하고, 결과는 메인 루프가 매 프레임 반영해 화면이 멈추지 않는다. 사람이 내린 판정은 늦게 온 AI 판정이 덮지 않는다. 8초 안에 판정이 없으면 기본 판정으로 진행한다. 형식이 틀린 응답은 버린다. 429·5xx 는 재시도한다. 키가 없거나 실패하면 키워드 해석·mock 판정으로 이어진다.
6. 엘프(트래픽 대응)의 AI 사용은 비용을 묶어 둔다: 경보마다 첫 판단만 묻고(재시도 없이 HTTP 1회), 한 번 실행에 최대 5회(`XMAS_AI_TRAFFIC_MAX`). 넘거나 실패·12초 지연이면 규칙(캐시 → 계산대 → 번호표 → 담당자)으로 움직인다. 요청을 거절하는 번호표는 AI 가 골라도 사람 승인 없이는 켜지 않는다.

## Ⅴ. 프로젝트 구현 결과 및 완성도

**○ 프로젝트 구현 결과 및 완성수준**

- **실제 작동 범위**: `python3 xmas_market.py` 하나로 타이틀부터 메뉴, 6개 서비스 × 3개 시나리오 스테이지까지 모두 동작한다. 외부 패키지와 API 키가 필요 없다. `OPENAI_API_KEY` 를 넣고 `--ai`(mock) 또는 `--live` 로 띄우면 AI 병정 모드(명령 해석·트리아지·브리핑)가 켜지고(mock 기본은 OpenAI 0회), `./run-with-codex.sh` 로 Codex 채팅과 나란히 띄운다.
- **테스트·검증**: `tests/test_smoke.py` 35개 + `tests/test_elf.py` 17개, 52개 테스트가 모두 통과한다(약 7초, 네트워크 없이).
  - 18개 화면 조합 렌더
  - 키워드 명령
  - 가짜 OpenAI 응답으로 확인하는 명령 해석·트리아지·브리핑
  - API 실패 시 폴백, 사람 판정 우선, 판정 타임아웃, 형식 오류 응답, 429 재시도, 판이 바뀐 뒤 도착한 결과
  - 녹화·재생, 가짜 Sentry 응답으로 확인하는 실연동(중복 방지·가짜 쥐 차단·읽기 실패 시 mock 폴백)
  - 가짜 /metrics 로 확인하는 트래픽 실연동(카운터 증가분 → rps, 서버 재시작·읽기 끊김, 가짜 급증 차단, 5xx 비율·응답 시간·Web Vitals)
  - 가짜 /metrics·가짜 레버·가짜 AI 로 확인하는 엘프(급증에 캐시 → 계산대 순 대응과 원복, 번호표 승인 전 미실행, 일반 대화로 승인되지 않음, 승인 없으면 담당자 호출, AI 예산 초과 시 규칙, 레버 없는 서버에서 켠 척 안 함, 레버 변경 직후 옛 지표로 덮어쓰지 않음)
  - 구현 뒤 [작성: 누가 리뷰했는지 — 사람/AI 도구명] 코드 리뷰를 거쳐, 지적된 결함 5건(사람 판정 덮어쓰기·판정 대기 고착·이상 응답 처리 등)을 고치고 회귀 테스트로 고정했다.
- **AI 트리아지 정확도 평가 (실제 API)**: 정답을 붙인 Sentry 이슈 제목 32건(fixable 14 · noise 10 · needs-human 8)을 `tools/eval_triage.py` 로 gpt-5-mini 에 판정시켰다. 결과는 **정확도 29/32 = 90.6%**, 평균 응답 4.2초, 호출 실패 0건이다(`docs/eval/triage-gpt-5-mini.md`). 사람이 꼭 봐야 하는 needs-human 8건은 모두 맞혔다. 틀린 3건(브라우저 저장소 차단, JSON 대신 HTML 응답, 출처 불명 Promise 거부) 중 2건은 사람에게 넘기는 보수적 오판이고, 1건(fixable → noise)은 실제 버그를 놓치는 방향이다. 평가셋은 직접 만든 32건(제목만, 1회 실행)이고 프롬프트 예시와 유형이 겹쳐, 실제 이슈에서는 더 낮을 수 있다. 시연 화면(`docs/images/ai.png`·`ai-history.png`)도 실제 API 호출로 찍었다(13회 호출, 실패 0).
- **Sentry 실연동 검증**: 테스트용 Sentry 프로젝트에 데모 웹앱(merrybugmas/demo-web, 일부러 심은 버그 7종)을 붙였다. 브라우저에서 난 실제 에러가 Sentry 이슈가 되고, 대시보드(`--live`)가 그것을 읽어 쥐로 만드는 것까지 확인했다. 실제 서비스의 이슈로는 검증하지 않았다.
- **실제 수정 PR 검증**: 데모 웹앱의 실제 Sentry 이슈 7건으로 돌려 49초 만에 PR 3개가 열렸다(merrybugmas/demo-web #1~#3: 쿠폰 null 방어, 목록 items 확인, Invalid Date 방지, 각 1~3줄). 백엔드 5xx 2건·HTML 을 JSON 으로 읽는 에러 1건은 사람에게, 광고 스크립트 1건은 noise 로 보냈다. OpenAI 호출 10회, 실패 0. #1~#3 은 다음 시연을 위해 "시연 정리로 닫음" 코멘트와 함께 닫았다(머지하지 않음). 이후 실행에서는 앞서 사람에게 넘겼던 HTML→JSON 파싱 에러(WEB-J)를 fixable 로 판정해 PR #4(`/api/notice` 응답이 HTML 일 때 JSON.parse 방어, 5줄)를 열었다. 같은 이슈라도 실행마다 판정이 달라질 수 있다는 뜻이라 제약사항에 적었다. 머지는 사람이 한다.
- **트래픽 실연동 검증**: 같은 데모 서버의 `/metrics` 를 읽었다. 부하 생성기로 25 → 110 → 25 rps 를 주자 대시보드 rps 가 그대로 따라가고 줄이 인파 경보까지 늘었다. 요청의 15% 를 503 API 로 보내자 5xx 비율이 14% 대로 표시됐고, 브라우저가 실제로 잰 Web Vitals(LCP·CLS·TTFB)도 표시됐다. 로컬 서버 한 대 기준이며 실제 서비스 트래픽으로는 검증하지 않았다.
- **트래픽 대응(엘프) 검증**: 데모 서버에 동시 처리 슬롯 제한(기본 2)과 레버를 넣어, 트래픽이 몰리면 실제로 밀리고 레버를 당기면 실제로 풀리게 했다. 110 rps 급증에서 그대로 두면 5xx 15% · 평균 응답 769ms, 캐시만 켜면 0% · 46ms, 캐시 + 슬롯 4 면 0% · 25ms, 번호표만 켜면 5xx 대신 429 35%. 엘프 자동 대응(규칙, AI 끔)으로 25 → 110 → 25 rps 를 주자 6초에 경보 → 캐시 → 16초에 계산대 4 → 26초에 해소(5xx 16.9→0.1%, 응답 994→76ms) → 급증이 끝난 뒤 계산대·캐시를 원복했다. 구현 뒤 AI 코드 리뷰에서 지적된 결함(일반 대화로 번호표가 승인되던 문제, 승인 대기 고착, 경보 한 번에 AI 를 여러 번 부르던 문제 등)을 고치고 회귀 테스트로 고정했다.
- **현재 제약사항**:
  - 기본 실행은 트래픽·이슈 모두 mock 이다. `--live` 에서만 실제 Sentry 이슈와 실제 서버 rps 를 쓰며, 테스트 프로젝트·로컬 데모 서버로만 검증했다.
  - 트리아지 입력은 이슈 제목뿐이다. 명령 해석·브리핑은 정량 평가를 하지 않았다.
  - Codex 연동은 규약·스크립트까지 구현했고, 지출 한도로 최종 실행 검증을 못했다.
  - AI 판정은 실행마다 달라질 수 있다: 같은 이슈(WEB-J)를 한 번은 needs-human, 다음 실행에서는 fixable 로 판정해 PR 을 열었다. 그래서 PR 은 열기만 하고 머지는 사람이 한다.
  - mock 이슈의 fix·review·MR 은 연출이다. 실제 PR 은 실연동 이슈에만 열리고, 데모 웹앱처럼 작은 레포의 한두 줄 수정까지만 확인했다. 병정의 review 단계는 연출이며 실제 리뷰는 사람이 한다.
  - 엘프의 레버는 데모 서버(localhost)에만 있다. 실제 서비스라면 캐시·오토스케일·대기실을 API 로 여닫는 운영 도구에 연결해야 한다. mock 모드의 엘프 5xx·응답 시간은 부하로 추정한 값이다. 엘프의 AI 판단은 가짜 응답 테스트로만 확인했고 실제 API 로 정량 평가하지 않았다.
  - macOS · Python 3.9 에서 확인했다. Linux · Python 3.8 은 문법 호환만 확인했다(Windows 는 WSL).

## Ⅵ. 실용성 및 문제 해결 효과

**○ 주요 활용방안 및 문제 해결 효과**

- **장애 대응 상황판**: 배포 직후 에러가 몰리면 쥐 떼가 나오고, 병정이 자동으로 분류한다. 운영자는 needs-human 우리에 갇힌 쥐만 보면 된다. 확인해야 할 화면이 셋(Grafana·Sentry·봇 로그)에서 하나로 준다(기대 효과). 평가 32건 기준으로 AI 가 사람에게 올린 것은 10건이라 운영자가 볼 이슈가 약 69% 줄었고, 사람이 봐야 할 8건은 하나도 놓치지 않았다(직접 만든 평가셋 기준).
- **트래픽 폭주 1차 대응 자동화**: 특가 오픈처럼 요청이 몰리면 엘프가 위험이 낮은 조치(캐시·증설)부터 즉시 하고, 효과를 숫자로 확인해 로그에 남긴다. 요청을 거절하는 조치(번호표)는 사람에게 묻고, 레버로 못 푸는 API 장애는 사람에게 넘긴다. 잠잠해지면 원복까지 해서 "켜 놓고 잊은 임시 조치"가 남지 않는다.
- **봇 판단의 투명성**: 모든 판정에 근거 한 줄이 붙고 기록으로 남는다. 잘못된 판정은 채팅 한 줄("WEB-2B1 사람에게")로 바로잡고, 그 결정은 AI 가 다시 덮지 않는다. 자동화를 사람이 감독하는 구조다.
- **말로 하는 운영**: 명령어를 외우지 않아도 "제일 오래된 쥐부터", "검색 쪽 503 에러 난 거" 같은 표현으로 지시할 수 있다.
- **실연동 비용이 낮음**: Sentry 는 이미 붙였다. `.env` 에 토큰·조직·프로젝트 세 값을 넣고 `--live` 로 띄우면 그 프로젝트의 미해결 이슈가 쥐가 된다(읽기 전용이라 운영 중인 Sentry 에 영향이 없다). 트래픽도 서버의 `/metrics` 주소 하나만 넣으면 실제 rps 로 줄을 세운다(Prometheus 형식 카운터가 있는 서버면 된다). 여러 서버를 합친 Grafana 지표를 읽는 일은 남았다. 트리아지는 이미 실제 LLM 호출이고, 입력을 이슈 제목에서 스택트레이스로 넓히는 것이 다음 단계다.

## Ⅶ. 차별성 및 확장 가능성

**○ 기존 방식 또는 유사 서비스 대비 차별점**

- 기존 대시보드(Grafana·Sentry)는 숫자를 보여 주는 데서 끝난다. 이 프로젝트는 에이전트의 행동과 판단 근거를 보여 주고, 같은 화면에서 채팅으로 그 에이전트를 지휘한다.
- 운영자 에이전트(Codex)와 실행 에이전트(병정·엘프, OpenAI API)를 나눈 2층 구조다. 실행 에이전트는 에러(병정)와 트래픽(엘프) 두 갈래이고, 둘 다 "감지 → 판단 → 조치 → 확인"을 화면에 보여 주며 위험한 조치는 사람 승인을 받는다. 사람은 대화하고, Codex 가 명령으로 바꾸고, 병정이 실행한다.
- 의존성 없는 터미널 앱이라 SSH 접속 서버나 tmux 에서도 바로 뜬다. 게임 연출로 운영 흐름을 직관적으로 전달한다.

**○ 향후 기능 고도화 및 사용자·활용분야 확장 가능 내용**

- Grafana·Prometheus 쿼리로 여러 서버 트래픽 합산, 병정 하나를 실제 sentry-bot(Codex) 수정 런 하나에 연결해 여러 파일에 걸친 큰 수정까지 PR 로
- 트리아지 입력에 스택트레이스·관련 소스 추가, 실제 Sentry 이슈 수백 건으로 평가 확대, 자동 수정 PR 의 머지율 측정
- Slack 알림, 웹 버전(같은 state.json 을 브라우저에서)
- 다른 테마·지표: 결제 실패 = 화재, 배포 = 썰매, CI 실패 = 눈사람 붕괴 등. 데이터 파이프라인·고객문의 큐로 확장

## Ⅸ. 팀 학습 및 협업 과정

**○ 스터디 과정의 주요 학습·논의 내용 및 프로젝트 구현 연계**

> 초안: 레포에 남은 결과물로 쓸 수 있는 내용이다. 스터디에서 실제로 나온 논의로 고쳐 쓴다.

- **에이전트에게 규약 문서 주기 (Codex · AGENTS.md)**: 에이전트에게 "쓸 수 있는 도구 + 지켜야 할 행동"을 문서로 주면 프롬프트를 매번 쓰지 않아도 된다는 점을 배웠다. 이를 `AGENTS.md` 로 옮겨, 운영 채팅이 답하기 전에 반드시 `./market status` 를 읽고 숫자로 답하고, 코드를 고치지 않고, 번호표·PR 머지는 사람에게 묻도록 했다. 코드를 고치러 온 에이전트에게는 따로 `docs/architecture.md`(파일 지도·불변식·같이 고칠 곳)를 주어 역할을 나눴다.
- **Structured Outputs**: 자유 텍스트 답을 파싱하면 게임 동작이 쉽게 깨진다는 논의에서, 명령 해석·트리아지·브리핑·엘프 레버·수정 패치 다섯 가지를 모두 strict JSON Schema 로 받게 했다. 스키마를 벗어난 응답은 버리고 키워드·규칙으로 넘어간다.
- **에이전트를 믿고 맡기려면**: 사람 판정이 늦게 온 AI 판정에 덮이지 않게, 판정이 늦으면(8초) 기본값으로, 판이 바뀐 뒤 온 결과는 버리게 했다. 되돌리기 어려운 조치(요청 거절, PR 머지)는 사람 승인으로 남겼다.
- **비용을 설계에 넣기**: 크레딧이 적었던 실제 제약이 설계로 이어졌다. mock 모드는 OpenAI 0회, 엘프는 경보마다 첫 판단만·실행당 최대 5회, 수정 PR 은 실행당 최대 `XMAS_FIX_MAX`, 키 없이 AI 결과를 보여 주는 녹화 재생(`--replay`)을 만들었다.
- **측정으로 말하기**: "AI 가 잘 판정한다"는 말 대신 정답을 붙인 32건으로 정확도(90.6%)·혼동 행렬·응답 시간을 쟀고, 틀린 3건과 평가셋의 한계를 그대로 적었다. 엘프도 레버별 5xx·응답 시간을 실측해 비교했다.

## Ⅹ. 기타

- **기획 의도**: 연말 특가처럼 트래픽이 몰리는 시즌의 장애 대응은 숫자와 알림이 쏟아져 긴장되는 일이다. 이를 크리스마스 마켓 장면으로 바꿔, 지금 무슨 일이 일어나고 에이전트가 무엇을 하고 있는지를 누구나 한눈에 보고, 말로 지휘할 수 있게 하고 싶었다.
- **키 없이 보는 순서 (약 2분)**: `python3 xmas_market.py --replay` → 아무 키 → WEB · 🐭 Sentry 버그 · START → `b`(쥐 떼) → 병정의 판정 근거가 작전 로그(🧠)에 뜨는 것 확인 → `r`(잡은 쥐 기록: 건마다 판정·근거·수정 요약) → `1`(트래픽) → `t`(급증: 엘프가 캐시 → 계산대 순으로 대응) → 다른 터미널에서 `./market tell 엘프 보고`, `./market tell 진저 보고`.
- **시연영상에서 볼 것**: 실제 Sentry 이슈가 쥐로 나타남 → AI 판정 → 병정이 GitHub PR 을 엶(PR 링크) → 부하 급증에 엘프가 데모 서버의 실제 레버를 당겨 5xx·응답 시간이 내려감 → 채팅(Codex)으로 현황 질문·지휘.
- **결과물 링크**: 코드 https://github.com/merrybugmas/merrybugmas · 데모 웹앱과 병정이 연 PR https://github.com/merrybugmas/demo-web/pulls?q=is%3Apr
- 모든 수치(정확도, 5xx·응답 시간, PR 수)는 레포 문서(`docs/eval/`, `docs/traffic-agent.md`)와 PR 기록에서 다시 확인할 수 있다.
